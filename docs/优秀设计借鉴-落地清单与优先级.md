## P0 —— 安全缺口 / 数据正确性，立即做

### P0-1 网关身份头 HMAC-SM3 签名闭环

**现状与差距**：`ct-gateway/.../AuthFilter.java` 验完 token 后**明文**透传 `user_key/user_id/username` 头，内网直连下游服务即可伪造身份头绕过网关。
**做法**（壳抄 MateCloud，内核换国密）：
- 签名工具放 ct-common-core：规范化拼串（参数名 ASCII 排序、空值不参与，风格对齐现有 `EnvelopeCanonical`）→ `HmacSm3.hmac(internalSecret, 串)`（本仓 `common/core` crypto 包 `HmacSm3`，`FieldIndexUtils` 已在用）；比对用常量时间比较。
- 网关加 IdentitySignFilter（AuthFilter 之后）：追加 `X-Gateway-Ts` / `X-Gateway-Nonce` / `X-Gateway-Sign`；同时剥除入站自带的 `X-Gateway-*` 伪造头。
- 防重放复用 ct-auth 的 `RedisNonceCache`（SETNX+TTL，fail-open 策略保持一致）。
- 下游验签组件放 ct-common-security（Filter + `enabled/skip-paths` 配置），借鉴 CPF SqlInjectionFilter 的 **ALERT→BLOCK 双模式**灰度：先 ALERT 观察一周再切 BLOCK。
- 密钥 `ct.gateway.internal.secret` 走 Nacos 加密配置/环境变量，为空拒绝启动（MateCloud 的 fail-fast 约定）。
- MateCloud 参考：`mate-common/mate-base/.../security/GatewaySignature.java`、`mate-gateway/.../filter/HeaderRelayFilter.java`、`SecurityHeaderFilter.java`。
**验收**：直连下游伪造 `X-User-Id` 被拦；网关正常链路无感；开销 = 一次 HMAC + 一次 Redis SETNX。

### P0-2 Dubbo 消费端超时/重试治理

**现状与差距**：全部 `@DubboReference` 只配了 `check=false`，走默认值：timeout=1s（偏紧）、retries=2 + cluster=failover——**失败自动重试 2 次，非幂等操作（登录、记录日志、注册）最多执行 3 次**，是数据正确性风险。另 `police-collector` 的 `DubboAuditBridge` 连 check 都没配（默认 true，provider 未起时 collector 启动失败）。
**做法**：
- defaults.yml 统一 consumer 默认：`timeout: 3000 / check: false / cluster: failover`（MateCloud 的用法：`@DubboReference(check=false, timeout=5000, retries=1)`）。
- 逐方法确认幂等性，**非幂等**显式 `@DubboReference(retries = 0, cluster = "failfast")`。
- 修 DubboAuditBridge。
- ⚠️ 本地 yml 可能非全量（最终配置源在 Nacos），落地前先核对 Nacos 有无 `dubbo.consumer` 段；另核实部分服务 yml `protocol.name: dubbo` 与注解 `protocol="tri"` 的混配。
**验收**：所有引用点超时/重试策略显式；登录等非幂等调用不再重复执行。

### P0-3 TripleExceptionFilter 兜底信息泄漏修复

**现状**：`ct-common-security/.../dubbo/TripleExceptionFilter.java` 的 `convert()` 兜底分支 `AjaxResult.error(e.getMessage())`，未预期异常把内部消息（类名、可能的 SQL 细节）直透前端。
**做法**：兜底改通用文案，详情只进日志（带 traceId）。几行改动。
**验收**：构造未预期异常，前端只见通用错误，日志有完整堆栈。

## P1 —— 稳定性风险，压力/发布时显形

### P1-1 优雅下线

**现状**：`server.shutdown`、dubbo shutdown、K8s preStop 全无，滚动发布掐断在途请求。
**做法**：`server.shutdown: graceful`（配 `spring.lifecycle.timeout-per-shutdown-phase`）+ `dubbo.provider.shutdown` + 部署层 preStop sleep（CPF 文档 11.5.4 的方向是对的，注意其代码里并无实现，按待补齐项对待）。
**验收**：kill 期间在途请求正常返回，新请求摘除。

### P1-2 内部调用熔断限流（Sentinel Dubbo Adapter）

**现状**：Sentinel 只在网关；内部 Dubbo 调用一个下游变慢会耗尽调用方默认 200 线程，雪崩沿调用链传导，网关挡不住内伤。
**做法**：引入 `dubbo-sentinel` adapter（CPF 11.5.5 推荐方式：引依赖即生效，资源名=interface#method），规则继续走 Nacos 持久化 + 现有 dashboard。**不引 Resilience4j**，避免双熔断体系并存。
**验收**：模拟下游慢调用，调用方半开熔断并有 fallback 日志。

### P1-3 Kafka 消费容错（DLQ + 指数退避 + 幂等）

**现状**：ship-collector / ct-alert / data-aggregate / metadata-service 四个用 Kafka 的服务无任何 ErrorHandler/DLQ 配置，spring-kafka 默认重试 9 次后**跳过并记日志 = 静默丢消息**（ct-alert 丢告警没人知道）。
**做法**（CPF 那套，Boot 3.5 核对 API 后收编）：
- `DefaultErrorHandler` + `DeadLetterPublishingRecoverer`（`{topic}.dlq`）+ `ExponentialBackOff`（200ms→×2→max 5s）；
- 消费幂等 `IdempotentChecker`（Redis SETNX processing→done 状态机）；
- 生产端参照 `ReliableMessagePublisher` 思路补 confirm。
- 参考：`common/integration/.../config/KafkaIntegrationAutoConfiguration.java`、`.../sync/consumer/IdempotentChecker.java`。
**验收**：构造消费失败，消息指数退避后进 DLQ 可回放；同消息重复投递只处理一次。

### P1-4 有界异步线程池

**现状**：全仓无自定义 TaskExecutor，`@Async`（`AsyncLogService` 操作日志、`DubboRequestInterceptor`）用 Boot 默认池——**队列无界**，日志风暴时 OOM 风险。
**做法**：ct-common 定义 `applicationTaskExecutor` 覆盖默认（核心=CPU 核数、有界队列、`CallerRunsPolicy` + 拒绝日志），TaskDecorator 传递 traceId（参考 MateCloud `MateThreadContext` 快照/恢复思路）。
**验收**：压测下队列有界、拒绝有日志、@Async 内 traceId 不丢。

### P1-5 分布式锁三件套

**现状**：完全没有分布式锁。CPF 的实现是全仓库质量最高的可移植资产：`DistributedLock`（SETNX+TTL、Lua 校验 value 才删/续约、重试随机抖动防惊群）+ `LockLeaseManager`（TTL/2 自动续约 + @PreDestroy）+ `LockHandle`（AutoCloseable）。
**落点**：ct-common-redis。纯 spring-data-redis + Lua，改包名即用。注意 MateCloud 的锁是 Redisson 版，我们不引 Redisson，**抄 CPF**。
**验收**：多实例并发抢锁互斥、持锁进程重启锁可自动续约/释放。

### P1-6 @Idempotent API 幂等

**现状**：无任何接口防重机制。
**做法**：CPF `common/web/.../idempotent/` 的注解+切面：TOKEN（header）/PARAM（SpEL）/PATH（method+URI）三种 key 模式，SETNX+expire，业务异常删 key 允许重试。
**验收**：双击提交只生效一次；业务失败后可重试。

### P1-7 traceId 全链路贯通（新建 ct-common-trace）

**现状**：traceId 只在网关（`TraceIdFilter` 已生成并回写 `X-Trace-Id`，写得完整，不用动）；下游服务没进 MDC、Dubbo 调用不透传、业务服务 logback pattern 无 `%X{traceId}`——排障时日志串不起来。
**做法**（⚠️ 必须走 Dubbo Filter 层，Servlet Filter 层不适用——我们没有 MVC）：
- MateTrace（纯 SLF4J MDC 封装）照拿；
- Dubbo provider Filter：从 Triple REST 入站头（`RpcContext.getRequest(HttpRequest).getHeaders()`）或 attachment 读 traceId → 绑 MDC → finally 清理；consumer Filter：写 attachment。移植 MateCloud `TraceDubboConsumerFilter/ProviderFilter`（纯 attachment 实现、协议无关）后补 REST 入站头读取；
- SPI 注册照 ct-common-security 现有 `META-INF/dubbo` 做法；
- 各服务 logback.xml pattern 收敛带 `%X{traceId}`（注意服务自带 logback.xml 时 spring 的 logging.pattern 配置无效，必须动 logback.xml 本身）。
**验收**：网关 → 服务 A → Dubbo → 服务 B 的日志同 traceId；响应头带回 X-Trace-Id。

### P1-8 actuator 收编 + 健康检查

**现状**：仅 7 个服务引入 actuator，无自定义健康检查。
**做法**：defaults.yml 统一暴露策略（health/prometheus，内网限定）；启用 Druid/Redis 自带 indicator；CPF 的自定义 indicator（ReadWriteHealthIndicator/SlaveHealthChecker）是 PostgreSQL 方言 + Boot 4 包名，只抄"检查什么"的思路，不抄代码。
**验收**：所有服务 /actuator/health 覆盖 DB/Redis 状态。

## P2 —— 规范 / 能力补强 / 工程效率

### P2-1 ct-defaults.yml 配置收敛模式（低成本杠杆，排第一批）

MateCloud `mate-defaults.yml` 模式：打进 ct-common-core，各服务一行 `spring.config.import: classpath:ct-defaults.yml`，application.yml 只留差异。
**⚠️ 本项目修正**：**去掉 Jackson 段**——业务服务没有 Spring MVC（全仓无 @RestController，HTTP 入口是 Dubbo Triple REST，JSON 由 Dubbo 的 protobuf-json 映射层序列化，`spring.jackson.*` 管不到；Redis 用 FastJson2）。保留：日志 pattern 约定、Dubbo 参数（见 P0-2）、优雅下线（见 P1-1）、编码等。

### P2-2 两级缓存

MateCloud `mate-cache-starter`：`CompositeCacheManager/CompositeCache`（Caffeine L1 + Redis L2，标准 Spring Cache 抽象，@Cacheable 照用）+ `CacheSyncBroadcaster` 跨实例失效广播；`MateRedisKey` 声明式 key 定义。pom 已有 Caffeine，目前仅 collector 零散用。Boot 3.5 兼容。

### P2-3 JWT 会话强化

CPF `common/web/.../security/util/JwtUtils.java`（同为 jjwt 0.13，几乎无改）：设备绑定 Hash（多设备管理/单设备踢出）、jti 黑名单、fingerprint、refresh 并发刷新锁（SETNX 5s）+ 旧 token 旋转。现状只有单一 Redis 会话 key。等保加分项。

### P2-4 Flyway 规范

MateCloud：每服务独立历史表 `table: flyway_history_${module}`（我们 ct-modules 服务多、共用 Oracle 库，避免版本撞号）、`repair-on-migrate: true`、种子数据全幂等。注意其 `INSERT IGNORE` 是 MySQL 方言，Oracle 改 `MERGE INTO`。另有存量库历史拆分脚本 `scripts/flyway-split-history.sql` 思路可参考。

### P2-5 网关动态路由

MateCloud `DiscoveryMetadataRouteLocator`：服务在 Nacos metadata 声明 `gateway-path`，网关自动生成路由并定时刷新，**新增服务零网关改动**。纯 SCG 原生 API。

### P2-6 读写分离写后读一致性窗口

我们已有 dynamic-datasource @Master/@Slave，但无写后读窗口。移植 CPF `ReadWriteRoutingContext` 的 `markWrite()/shouldUseMaster()`（写事务提交后 N 秒强制走主库）为切面增强；其 `ReadWriteRoutingCleanupFilter`（请求结束清 ThreadLocal 防串号）一并参考。从库熔断（SlaveCircuitBreaker）并入 P1-2 的 Sentinel 体系考虑。

### P2-7 DataScope 防注入三层校验

CPF `DataScopeInterceptor` 拦截的是**原生 MyBatis StatementHandler**（与 PageHelper 兼容，架构可直接搬），其三层防注入设计（`isSafeFilter` 黑名单 + `matchesAllowedPattern` 白名单 + `validateSqlIdentifier` 别名校验）即使不全套引入也值得抄进现有 `DataScopeAspect`。注意其五级权限实现含 PG 方言（`::uuid`、递归 CTE），Oracle 化需删 `::uuid`、改 `CONNECT BY`。

### P2-8 开放接口签名统一 HmacSM3

collector 的 `AkSkSigner.java:21` 已留 TODO："接口规范下发后若要求国密 SM3-HMAC，替换算法并保持本类对外方法不变"。借 P0-1 的签名工具落地，顺带补 nonce 防重放（对齐 MateCloud sign 包的 `@ApiSign + CachedBodyFilter` 结构）。

### P2-9 starter 化改造（渐进）

现状已是 Boot 3 `AutoConfiguration.imports` 机制（8 个模块都配了），但 imports 直接列具体类（RedisService/AsyncLogService 等），无 `@AutoConfiguration` 包装、无条件注解、无默认配置。改造：每模块 → `@AutoConfiguration` + `@ConditionalOnClass/@ConditionalOnProperty(prefix="ct.xxx", matchIfMissing=true)` + `@ConfigurationProperties` + 模块内 defaults；`@EnableCustomConfig` 里的 @MapperScan/@EnableAsync/exposeProxy 职责逐步下沉到各 starter。

### P2-10 Testcontainers 集成测试基座

MateCloud `mate-test-starter`：`@MateIntegrationTest` 元注解 + ContainerInitializer（withReuse 复用容器）+ `@Disabled` 标注依赖 Docker。MySQL 容器换 Oracle 镜像。

### P2-11 ct-auth 登录策略模式重构（渐进，成本大）

MateCloud `LoginStrategyFactory/AbstractLoginStrategy`（Spring 注入 List 注册，重复注册启动即报错）+ 端口防腐层（`TokenIssuerPort/RefreshTokenPort/PasswordEncoderPort`…，换 token 实现只动 infrastructure）。ct-auth 已有密码/2FA/国密信封多条路径，适合按此模式重构 `SysLoginService`，作为中长期方向，不急。

### P2-12 Kafka 消息信封 MessageEnvelope（随 P1-3 同批）

CPF 的 CloudEvents 风格信封（id/type/source/subject/time/traceId/tenantId/version/data），纯 Java 直接抄，统一四个 Kafka 服务的消息格式并带 traceId。

### P2-13 DevOps 借鉴（可选）

MateCloud：参数化多阶段 Dockerfile（ARG MODULE_PATH 单文件构建全部服务、thin jar 甄别、非 root 用户）、docker-compose 健康检查、Makefile 统一入口。我们有 Jenkinsfile，按需吸收。

## 明确不做（防止过度设计）

| 项 | 理由 |
|----|------|
| 多租户（MateCloud tenant-starter） | 政务单租户；SQL 层还锁 MyBatis-Plus |
| Sa-Token / Spring Security 全套 | jjwt 自建体系已跑通（2FA/国密信封），替换成本 > 收益 |
| MyBatis-Plus 系实现（BasePO/TenantLine/MP InnerInterceptor） | 我们是原生 MyBatis + PageHelper |
| Resilience4j | 已有 Sentinel，避免双熔断体系 |
| CPF 的 Sentinel 自研封装（RateLimitAspect/StepUp 熔断层） | 依赖我们不存在的应用侧 Sentinel 接入方式 |
| DDD 4 层 / CQRS / 存量重构 | 与现有 RuoYi 分层不匹配，不硬靠 |
| MateCloud mq-starter 的 RabbitMQ 部分 | 我们主要用 Kafka（其 EventPublisher/DLQ 是 spring-amqp 系） |
| MateCloud web-starter 的 MVC 组件（GlobalExceptionHandler/ResponseAdvice/Jackson 配置） | 无 MVC，等价物已有（TripleExceptionFilter）；详见 P0-3/P2-1 |

## 两份解读文档与实际代码的出入（借鉴时注意）

1. **CPF 文档夸大项**（代码中不存在）：Dubbo `check:false/retries/cluster/shutdown` 加固配置（`@DubboReference` 实际无参数，且其示例注入方式可疑，勿照抄）；Resilience4j `@CircuitBreaker` 注解用法（全仓零命中，熔断只靠 Feign 集成）；HikariCP `leak-detection-threshold`。这几条按"待补齐项"对待。
2. **CPF 方言/版本耦合**：数据权限与健康检查含 PostgreSQL 硬编码（`::uuid`、`WITH RECURSIVE`、`pg_last_wal_*`）；`org.springframework.boot.health.contributor` 与 `JacksonJsonRedisSerializer` 是 Boot 4/Spring Data Redis 4 类名，Boot 3.5 编译必失败。
3. **MateCloud 版本/框架耦合**：实际运行在 Java 21 + Boot 4.0.8 + Jackson 3；datascope/tenant 的 SQL 层锁 MyBatis-Plus，token 层锁 Sa-Token，分布式锁/限流锁 Redisson——这几小块只抄设计。其余（Result/trace/缓存组合/网关签名/Flyway/DevOps/CLI）与文档相符，无明显夸大。

## 附录 A：MateCloud starter 逐件可用性盘点

> 结论：16 个核心 starter + 8 个 contrib，**没有能整个照搬的**（整体是 MyBatis-Plus + Sa-Token + Boot 4 生态）；
> 拆到能力件粒度：**直接可用 7 件、小改可用 9 件、不适用约 12 件**。规律：凡 MateCloud 锁 Redisson/RabbitMQ 的件（锁/幂等/限流/MQ），设计抄 MateCloud、实现换 CPF（CPF 同名件是纯 Redis/Kafka 的）。

### A.1 直接可用（改包名/换内核即可）

| 来源 starter | 拿什么件 | 说明 | 对应清单 |
|---|---|---|---|
| mate-rpc-starter | TraceDubboConsumer/ProviderFilter | traceId 跨 Dubbo 透传，协议无关，同 Dubbo 3.3.6 零适配 | P1-7 |
| mate-cache-starter | CompositeCacheManager/CompositeCache、CacheSyncBroadcaster、MateRedisKey | 纯 Spring Cache + Redis + Caffeine，Boot 3.5 兼容 | P2-2 |
| mate-security-starter | AuditLog 三件套（注解+切面+事件） | 纯 Spring 事件解耦+脱敏，优化现有 @Log | P2 |
| mate-security-starter | EncryptTypeHandler | 全仓唯一原生 MyBatis TypeHandler（非 MP）；对接 SM4 只改密钥源；与 zdhr-crypto-mybatis 重叠，先确认 | 可选 |
| mate-monitor-starter | Micrometer/Prometheus 装配 | 配置级 | P1-8 |
| mate-test-starter | @MateIntegrationTest + 容器初始化器 | 换 Oracle 镜像 | P2-10 |
| mate-base 单件 | MateTrace、AuthHeaders、GatewaySignature | GatewaySignature 内核换 HmacSm3 | P0-1/P1-7 |
