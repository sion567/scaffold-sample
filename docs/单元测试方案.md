# ct 工程单元测试（JUnit 5）方案

> 2026-09 配套落地：3 类示例测试已提交并全部通过（ct-system 17 个、ct-auth 8 个），
> 本文是扩展指南——后续新增类的测试按第 5 节的「类 → 模式」对照表抄对应示例即可。

## 1. 现状与原则

- 全工程此前零测试依赖（无 junit/mockito/testcontainers，仅 ct-api-file 有空 src/test 目录）。
- 根 pom 已 import `spring-boot-dependencies` BOM，`spring-boot-starter-test` / `h2` 都**不需要写版本号**。
- 约束：不用 Testcontainers（重）；不依赖 Nacos/Redis/Oracle/网关即可跑；`mvn test` 全绿且秒级。

**总原则：不启动 Spring 容器。** 工程的 Service/Resource/Mapper 全部是构造注入的普通 Bean，
Mockito 直接打桩即可；启动 `@SpringBootTest` 会强依赖 Nacos + Redis + Oracle，不在默认测试里出现。

## 2. 测试分层

| 层 | 覆盖对象 | 依赖 | 运行时机 |
|---|---|---|---|
| L1 纯单元 | Resource / Service / Dubbo 提供方·消费方 / 工具类 / 拦截器 | Mockito | 每次 `mvn test`，毫秒级 |
| L2 数据层切片 | Mapper + 真实 mapper XML 的 SQL | H2 内存库（MODE=Oracle）+ 原生 MyBatis | 每次 `mvn test` |
| L3 真实库门禁（可选） | H2 模拟不了的方言（CONNECT BY、Oracle 专有函数等） | 环境变量指向真实 Oracle/达梦，或 Testcontainers 一次性容器（见第 9 节） | 默认跳过，按需触发 |
| L4 全组件联动（预留） | @SpringBootTest 全上下文 + Nacos/Redis/Kafka/Oracle 容器冒烟 | Docker + Testcontainers（见第 9 节） | 仅 CI 带 Docker 的 job 手动触发 |

L3 的落地方式（不需要 Docker 的轻量做法）：测试类加 `@Tag("db-it")` 和
`@EnabledIfEnvironmentVariable(named = "DB_IT_URL", matches = ".+")`，
`DB_IT_URL/DB_IT_USER/DB_IT_PASSWORD` 指向开发环境的达梦/Oracle；不设变量时 surefire 直接跳过。
达梦驱动（DmJdbcDriver18）加 test scope 即可。

## 3. 依赖接入（每个被测模块加一次）

**推荐：统一引入 `ct-test-starter`**（ct-starters 聚合下的测试支持组件），版本由根 pom
dependencyManagement 收口：

```xml
<dependency>
    <groupId>com.ct</groupId>
    <artifactId>ct-test-starter</artifactId>
    <scope>test</scope>
</dependency>
```

它收口了 JUnit 5 + Mockito + AssertJ + H2（+ 原生 MyBatis），并提供
`@H2JpaTest` 注解（见第 4 节例子 C）。两条使用约束：

- **必须以 test scope 引入**（组件内部依赖是 compile scope，靠接入方的 test scope 压下去，
  避免测试库混进生产包）；
- 组件**不做 Spring 自动装配**——我们的单测本来就不启容器，它只是依赖收口 +
  `@H2JpaTest`/扩展实现，不要往里塞业务 fixture 或自动配置类。

不需要 `@H2JpaTest` 的模块（如 ct-auth）也可以只用裸依赖（版本同样由 BOM 管理）：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>
```

已接入模块：`ct-modules/ct-system`（ct-test-starter）、`ct-auth`（starter-test）。
surefire 不用配置，Maven 3.9 自带版本可识别 JUnit 5。

新模块写 Mapper 测试时直接拷贝 C 的 `@BeforeAll` 骨架，改三处：H2 建表脚本（对照该模块
`db/migration/oracle/V*.sql` 的列集）、mapper XML 路径、别名注册。

注意点（实测踩过）：

- `AjaxResult.success(String)` 命中的是 **msg 重载**而非 data（RuoYi 遗留行为），断言值位置时留意（见例子 A 的 `getConfigKey` 用例）。
- H2 identity 序列不感知显式插入的主键，种子数据用了显式 id 后要 `ALTER TABLE ... RESTART WITH n`（Oracle/达梦导数对齐序列同理）。
- 测试加载 XML 用 `XMLMapperBuilder.parse()` 时接口会按 namespace 自动注册，**不要再 `addMapper`**（会抛 already known）。

### JJWT（ct-common-core 的 JwtUtils / 网关）测试模板

`JwtUtils` 是纯静态工具，密钥来自 `TokenConstants.SECRET`，直接往返断言。
在 `ct-common-core` 的 pom 加上第 3 节的 ct-test-starter 后，抄以下骨架：

```java
class JwtUtilsTest
{
    private Map<String, Object> claims()
    {
        Map<String, Object> claims = new HashMap<>();
        claims.put(Constants.LOGIN_USER_KEY, "userkey-uuid");
        claims.put(SecurityConstants.DETAILS_USER_ID, 1L);
        claims.put(SecurityConstants.DETAILS_USERNAME, "admin");
        return claims;
    }

    @Test
    void createThenParse_roundTrip()
    {
        String token = JwtUtils.createToken(claims());
        Claims parsed = JwtUtils.parseToken(token);
        assertEquals("admin", JwtUtils.getUserName(parsed));
        assertEquals(1L, JwtUtils.getUserId(parsed));
    }

    @Test
    void expiredToken_throws()
    {
        String token = JwtUtils.createToken(claims(),
                new Date(System.currentTimeMillis() - 1000));
        assertThrows(ExpiredJwtException.class, () -> JwtUtils.parseToken(token));
    }

    @Test
    void tamperedToken_throws()
    {
        String token = JwtUtils.createToken(claims()) + "x";
        assertThrows(SignatureException.class, () -> JwtUtils.parseToken(token));
    }
}
```

（异常类型按 jjwt 0.13 实际抛出的断言：过期 `io.jsonwebtoken.ExpiredJwtException`、
签名不符 `io.jsonwebtoken.security.SignatureException`。）

## 6. 数据库模拟选型：H2（不选 HSQLDB）

| 候选 | 结论 |
|---|---|
| **H2 `MODE=Oracle`** ✅ | 实测直接跑通工程的 Oracle 方言语句：`SYSDATE`、`FETCH FIRST n ROWS ONLY`、`NVL`、`TO_CHAR`、`INSTR`、`||` 连接、标准 `MERGE INTO`、IDENTITY 列、`useGeneratedKeys` 回填。且 `MybatisDatabaseIdConfig` 本来就内置了 H2 的 vendor 映射 |
| HSQLDB `sql.syntax_ora` ❌ | Oracle 兼容面比 H2 更窄（无 TO_CHAR 等），社区资料少，不引入 |
| Testcontainers ❌ | 按约束不使用；真实库诉求走 L3 门禁 |

局限：H2 不支持 Oracle 的 `CONNECT BY`、部分专有函数/包，覆盖到这类 SQL 的语句归入 L3。

**达梦迁移路径**：达梦与 Oracle 共用 `databaseId="oracle"` 语句，所以「L2 的 H2 测试 +
databaseId=oracle」验证的就是达梦上要跑的 SQL；上线前再用 L3 对真实达梦跑一遍全量 Mapper 测试即可。

### 6.1 官方 `@MybatisTest` 切片（评估结论：可选，不默认）

网上常见的 `@MybatisTest`（`org.mybatis.spring.boot:mybatis-spring-boot-test-autoconfigure`，
test scope）可以替代我们手写 `@BeforeAll` 组装 `SqlSessionFactory`：自动扫 Mapper、
自动开事务并回滚、支持 `@AutoConfigureTestDatabase(replace = NONE)` 保留自配数据源，
并会应用测试上下文里的 `DatabaseIdProvider` Bean。结论：

- **可用但不是必须**：它要拉起 Spring 切片上下文（约 1~2s/类），且 mapper 位置靠
  `mybatis.mapper-locations` 属性扫描——通配符会把目前**坏的** `mapper/system/oracle/` 目录一并扫进来
  直接解析失败（第 7 节），在修复前反而跑不了；
- 我们的手工组装方式零 Spring、精确控制加载哪些 XML、databaseId 设成什么，示例 C 保持现状；
- 若第 7 节修复完成且希望获得「自动回滚」便利，可按模块引入该 test 依赖 +
  `@MybatisTest` + `@TestConfiguration` 里注册一个把 **H2 映射为 "oracle"** 的
  `DatabaseIdProvider`（注意：与生产 `MybatisDatabaseIdConfig` 的 `H2→h2` 不同，
  测试里要映射成 oracle 才会跑到达梦/Oracle 方言语句）。

### 6.2 内存库缺函数的补法

网上 HSQLDB 的「伪函数注入」（`CREATE FUNCTION ... EXTERNAL NAME 'CLASSPATH:...'`）思路可借鉴，
但 H2 有更简单的原生等价写法——`CREATE ALIAS` 直接绑定 Java 静态方法：

```sql
CREATE ALIAS DECODE_SIM FOR "com.ct.test.H2Functions.decode";
```

测试建表脚本里加一行即可让 SQL 里的 `DECODE_SIM(...)` 跑通；仍属 L2 范畴，
真正要验证 Oracle/达梦原生函数行为时归 L3。

### 6.3 连接参数与时间函数约定（实测结论，H2 2.3.232）

`@H2JpaTest` 的默认 URL：`jdbc:h2:mem:<库名>;MODE=Oracle;DB_CLOSE_DELAY=-1;CASE_INSENSITIVE_IDENTIFIERS=TRUE`

- **`MODE=Oracle` 不能去掉**：SYSDATE、空串即 NULL、`FETCH FIRST`、`TO_CHAR`、`NVL`、`||` 全靠它。
  实测：插入 `''` 读回 `NULL`、`WHERE col=''` 命中 0 行、`SYSDATE` 可用——空串语义**模式自带，无需任何开关**；
- **`ORACLE_EMPTY_STRING_IS_NULL=TRUE` 是不存在的参数**（网上误传），写了直接报
  `Unsupported connection setting`；
- **`CASE_INSENSITIVE_IDENTIFIERS=TRUE` 默认已加**：兼容带引号的大小写混写 DDL
  （达梦/工具导出脚本常见），对齐 Oracle 标识符不区分大小写的语义；
- 需要追加参数时用 `@H2JpaTest(urlOptions = {"...=..."})`，不要改 starter。

**基础版语句时间函数统一用 `SYSDATE`**（而非 CURRENT_TIMESTAMP）：达梦/Oracle 原生、
H2 Oracle 模式可用，语义为数据库时钟、秒精度，与存量语句一致；CURRENT_TIMESTAMP 在
Oracle 上是「会话时区 + 微秒精度」，与 SYSDATE 混用会造成精度/时区不一致。
配套约定（基础版跨库通用写法）：`limit 1` → `FETCH FIRST 1 ROWS ONLY`、
`limit #{n}` → `FETCH FIRST #{n} ROWS ONLY`、`concat('%',#{x},'%')` → `'%' || #{x} || '%'`、
`date_format(t,'%Y%m%d')` → `TO_CHAR(t, 'YYYYMMDD')`、`find_in_set(#{x}, col)` →
`INSTR(',' || col || ',', ',' || #{x} || ',') > 0`、`sysdate()`/`now()` → `SYSDATE`。
`MODE=Oracle` 正是这些约定的强制检查器：MySQL 专用语法残留会被测试当场报语法错误，
而不是等到 Oracle/达梦上线才炸。

## 7. ⚠️ 实测发现的生产问题（与 databaseId 相关，迁达梦前必须修）

写 Mapper 测试时对 `mapper/system/oracle/SysUserMapper.xml` + `MybatisDatabaseIdConfig` 做了实测，
结论如下（MyBatis 3.5.19 源码 + 运行验证）：

1. **覆盖文件是坏的**：`<mapper namespace="..." databaseId="oracle">` —— mybatis 的 DTD
   **不允许** `<mapper>` 带 `databaseId` 属性（只能放在语句级元素上），该文件被
   `mapper/**/*.xml` 扫到就抛 `SAXParseException`，服务无法启动。
2. **DatabaseIdProvider 实际没生效**：`MybatisDatabaseIdConfig` 既不在 ct-common-mybatis 的
   `AutoConfiguration.imports`（里面只有 `MybatisAutoConfiguration`），也没被任何启动类扫描到
   （启动类只扫 `com.ct.<服务名>`），Nacos 配置里也没有 `mybatis.configuration.database-id`。
   → 生产（Oracle）当前 `databaseId=null`。
3. **由此推论生产现状**：Oracle 上执行的是主 mapper 的语句，其中
   `checkUserNameUnique/checkPhoneUnique/checkEmailUnique`（`limit 1`）、
   `selectUserList/allocatedList/unallocatedList`（`date_format`、`find_in_set`、`concat`）
   在 Oracle 上执行必然报错——即用户管理/角色分配部分功能在 Oracle 环境大概率是坏的。
4. **双文件覆盖模式在 MyBatis 3.5.x 走不通**（实测三种排列均失败）：
   - 主文件先加载 → 覆盖文件语句报 "Mapped Statements collection already contains key"；
   - 覆盖文件先加载 → 引用主文件 `<sql>` 片段时进 pending 队列延迟注册，同样重复冲突；
   - 覆盖文件自带同名片段 → "XML fragments ... already contains key"。
5. **正确做法**（`SysUserMapperDatabaseIdDemo.xml` 即模板，已验证）：
   - 把 `databaseId="oracle"` 的语句**直接并入主 mapper 文件**（同 id 双版本，MyBatis 自动按
     databaseId 优先/兜底），然后删除 `mapper/**/oracle/` 目录；
   - 把 `MybatisDatabaseIdConfig` 加进 ct-common-mybatis 的 `AutoConfiguration.imports`；
   - 补齐主文件里仍是 MySQL 语法语句的 oracle 版本（见第 3 条清单）。

> **【2026-09-10 核查】** `mapper/system/oracle/` 目录已不存在，本节所述问题已按上述方案修复；达梦迁移前请以当前 mapper 目录结构为准。

## 8. 运行与约定

```bash
mvn test                              # 全工程
mvn -pl ct-modules/ct-system,ct-auth test   # 指定模块
```

- 测试类与被测类**同包**放在 `src/test/java` 下；Mapper 测试的 DDL/种子脚本放
  `src/test/resources/sql/<模块>/*.sql`（UTF-8），由 `@H2JpaTest` 的 `ddl` 属性引用。
- 测试类命名 `XxxTest`，方法用 `@DisplayName` 写中文行为描述；一个测试方法只断言一条行为链。
- 不引入 `@SpringBootTest` 默认扫描；确需容器级验证的场景走 L3 门禁 / L4 联动（第 9 节）。

## 9. Testcontainers（预留方案，按需启用）

> 现状默认 `mvn test` **不引入**、不依赖 Docker。以下内容供后续需要「真实 Oracle / 达梦 /
> 全组件联动」时直接取用。版本号交给 `spring-boot-dependencies` BOM 管理（它已管理
> org.testcontainers 全家），**不用写版本号**。

### 9.1 依赖（启用时才加，test scope）

Nacos / Redis 无官方模块，用 `GenericContainer` 即可。junit-jupiter 模块自带
`@Testcontainers/@Container` 生命周期管理与 `@DynamicPropertySource` 注入。

### 9.2 L4 全组件联动基类（网上模板的工程化修正）

网上流传的 `BaseMicroserviceTest`（Oracle+Redis+Kafka+Nacos 四容器 + `@DynamicPropertySource`）
思路可用，直接照抄会踩本工程的坑，按下面修正：

1. **数据源属性路径不对**：本工程数据源走 dynamic-datasource（master/audit 双库），
   要注入的是 `spring.datasource.dynamic.datasource.master.url/username/password`（以及 audit、
   `spring.flyway.url` 独立 FLYWAY 连接），不是 `spring.datasource.url`；
2. **Nacos 2.x 的 gRPC 端口坑**：客户端按「主端口 +1000」推导 gRPC 端口，Testcontainers
   随机映射端口会导致推导落空。要么 `withFixedExposedPort(8848, 8848)` + `(9848, 9848)`
   固定映射（并行跑测试时注意端口独占），要么升级 nacos-client 显式配置；
3. **Network/别名非必需**：`@SpringBootTest` 在宿主机跑，连的是映射出来的宿主端口，
   `Network.newNetwork()` + aliases 只有把被测服务本身也容器化时才需要，可去掉简化；
4. **必须防「无 Docker 环境炸构建」**：基类标
   `@Testcontainers(disabledWithoutDocker = true)`，或放独立 maven profile / 只挂 CI；
5. Dubbo 侧同样注入 `dubbo.registry.address=nacos://<容器地址>`、`dubbo.protocol.port=-1`。

业务测试类继承该基类即可测「MyBatis 真库读写 + Redis + Kafka + Dubbo 注册」全链路，
适合作为少量冒烟用例，不作为常规单测载体。

### 9.3 真实达梦容器的正确姿势（网上写法有误）

网上示例的 `jdbc:tc:dm8:latest:///testdb` **不可用**——`jdbc:tc:` 前缀只认 Testcontainers
内置模块的数据库（oracle/mysql/postgres/mariadb/mssql/db2 等），达梦没有内置模块。
达梦要用 `GenericContainer` 手工管理：把官方 DM8 tar 镜像导入本地/内网镜像仓库后

```java
GenericContainer<?> dm = new GenericContainer<>(DockerImageName.parse("dm8-single:xxx"))
        .withExposedPorts(5236)
        .withEnv("CASE_SENSITIVE", "0");
String url = "jdbc:dm://" + dm.getHost() + ":" + dm.getMappedPort(5236);
```

再配合 `@DynamicPropertySource` 注入 dynamic-datasource；驱动 `DmJdbcDriver18` 加 test scope。
也可以完全不用容器，走第 2 节 L3 的环境变量直连开发环境达梦，效果等价、更省事。

## 10. Dubbo 直连集成测试（可选中间层，介于 L1 与 L4 之间）

网上「方案一消费者 Mockito」= 我们的例子 B1（已沉淀为 `DubboReferenceMocks.inject`）；
「方案三 `@DubboReference.url` 直连联调」属于联调环境技巧（`registry: N/A` + 按接口配
`url: tri://127.0.0.1:20880`），与单测无关。真正值得吸收的是**方案二：`DubboBootstrap`
本地直连暴露**——它比 L1 多验证两层真实行为：Triple 协议暴露与序列化、
本工程自定义的 Dubbo Filter 链（`SecurityContextFilter`、`TripleExceptionFilter`），又不依赖 Nacos。

已沉淀为 starter 的 `DubboDirectRuntime`（示例见例子 B3）：

```java
runtime = DubboDirectRuntime.tri()
        .service(RemoteUserService.class, impl)   // impl 手工 new、依赖 Mockito 打桩
        .start();                                  // 注册中心 N/A、随机端口、QoS 关闭
RemoteUserService consumer = runtime.consumer(RemoteUserService.class); // 直连真实 tri 端口
...
runtime.close();                                   // destroy + DubboBootstrap.reset()，同 JVM 可再次 start
```

实现要点（踩过的坑）：消费方必须复用提供方同一个 `ApplicationConfig`（Dubbo 3 同一模型
只允许一个应用配置）；`reference.setScope("remote")` 强制走真实端口，避免同 JVM 被
Injvm 调用短路。适用场景是需要验证 Filter 链/异常透出/真实序列化的少数关键链路——
单次启停约 1~10s，不作为常规单测载体。补充说明网上的序列化提醒：
本工程内部 RPC 全是 proto 消息（idl 生成），不存在「DTO 忘了 Serializable」问题；
JDK 21 虚拟线程 + RpcContext 的坑与本工程（Java 17）暂不相关，升级 JDK 后再看。

## 11.🌐 JUnit 9 大维度全景落地与断言验收指南

在微服务架构（Spring Cloud Alibaba + Dubbo + Oracle）中，一份合格的单元测试必须具备**场景构建的真实性**与**断言校验的严苛性**。为了统一团队的测试编写规范，特制定本指南。

### 🛑 团队落地执行红线（Code Review 标准）

1. **基础覆盖硬指标**：任何核心 Service/Mapper 代码合并前，对应的测试类必须至少覆盖 **维度 2（边界）** 与 **维度 5（异常）**。
2. **严禁盲目 `try-catch`**：在测试用例里，绝对不能为了不报错而写 `try-catch` 包裹代码。必须使用 `assertThrows` 明确断言异常。
3. **副作用断言是最高优先级**：凡涉及分布式锁（Redis）和本地事务（Oracle）的复杂业务，在测试抛出异常后，**必须编写对应的“锁状态验证”和“数据库回滚验证”断言**。


## 12. 拆分模块（common + web 服务 + kafka 服务）的测试组织

当前格局：`data-common`/`meta-common`（domain + mapper + service 共享库）+
`data-service`/`meta-service`（web：Triple REST Resource）+
`data-aggregate`/`meta-aggregate`（kafka：消费者）。两个服务连同一个库。

- **mapper 测试只放一份**：mapper 接口/XML 下沉在 common 模块，H2 切片测试就放 common
  （`@H2JpaTest` + 该模块自己的 DDL 副本），web/kafka 两个服务模块**不要再重复测 mapper**；
  若暂时放在服务模块（如当前 data-aggregate），另一服务引用同一 mapper 时只写业务层测试；
- **web 服务模块**：测 Resource 层（例子 A：Mockito mock 共享 service 接口），
  覆盖参数校验、R 包装、权限注解之下的分支；
- **kafka 服务模块**：listener 只做「反序列化 → 委托 service → 吞异常」，用 Mockito 覆盖三条
  契约——正常报文字段无损、毒消息不抛出、下游异常不外传（参考 `ShipPositionConsumerTest`）；
  真实 Kafka 交互归 L4；
- **共享库 DDL**：每个服务的测试 DDL 是各自的副本（`src/test/resources/sql/`），
  列集必须与 common 的 flyway 脚本对齐——`MODE=Oracle` 会把缺列/类型不符当场报出来；
- 注意 H2 陷阱：**VARCHAR 主键的表不要写 `ALTER TABLE ... RESTART WITH`**（仅数字 IDENTITY 列需要，
  且种子数据占用显式主键后必须 RESTART 推开序列）。
